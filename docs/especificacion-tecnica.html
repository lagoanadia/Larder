Los servicios gratuitos (Render/Groq) bajan de nivel o imponen límitesAlternativas de pago: Railway, Neon.
  • Railway vs Render: Railway cobra por uso real (lo que realmente consumes) en vez de dormir el servidor (apagarlo cuando no hay visitas) como hace Render gratis; Railway desde ~5$/mes, Render de pago desde ~7$/mes.
  • Neon vs Postgres (Render): Neon escala a cero (se apaga solo sin uso y no cuesta nada mientras tanto) y permite branches de la base de datos (copias de prueba para corregir un error sin arriesgar lo real); Neon de pago desde ~19$/mes.

2 los dos casos de uso

Un gesto para vaciar. Una foto para llenar.

Larder y List se retroalimentan: marcar algo como agotado lo manda a la lista; comprarlo lo devuelve a Larder.

Caso 1 · Marcar un item como "out" en Larder
QuiénCualquier miembro del hogar.
Pasos1. Ver productos con sus estados · 2. Click en "out" · 3. La app guarda el cambio y lo refleja · 4. Se añade a la lista de la compra.
ResultadoEl estado queda actualizado en la base de datos y aparece en List sin que nadie lo anote a mano.
Qué fallaFalta de conexión · dos personas cambian el mismo producto a la vez.
Caso 2 · Marcar como comprado un item dentro de List
QuiénCualquier miembro del hogar.
Pasos1. Sacar foto al ticket · 2. El item se repone automáticamente y se borra de la lista.
ResultadoList siempre refleja el estado real de Larder.
Qué fallaFalta de conexión.

4 la sección crítica

Dos personas, el mismo item, a la vez.

Servicios y Procesos.

preguntarespuesta
El recurso compartidoInteractuar a la vez con el mismo item.
La operación en conflictoLarder: marcar el mismo item como "out" dos veces en la lista — imposible. List: comprar dos veces es imposible porque habría que ir a la tienda a la vez.
Qué pasa hoyUsuario A abre List y ve "leche" pendiente. Usuario B abre List casi al mismo tiempo y ve el mismo item. Los dos lo marcan como comprado casi a la vez. Como hoy no hay ningún control de acceso a la pantalla, las dos peticiones se procesan igual — puede duplicarse el registro o quedar un estado inconsistente, sin que ninguno de los dos se entere de que el otro ya lo había hecho. En la práctica es poco probable (habría que ir a la tienda a la vez), pero el prototipo no lo impide.
Qué debería pasarNo dejar que dos usuarios abran List a la vez: el primero que entra se queda con el control de la pantalla, y el segundo recibe el mensaje "Alguien más está usando la lista ahora mismo, inténtalo en un momento" hasta que el primero la suelte. Así el conflicto no llega a producirse.
  • Tarea en segundo plano
    Restock automático de Larder · marcado de "comprado" automático · recuento de deudas automático · evento: compra automática.

Lo corrige: Concurrencia (CE2.5, CE2.6) · Tarea en segundo plano (CE1.6, CE2.2) · Depuración y documentación (CE2.8).

5 modelo de datos e integraciones

Seis tablas, dos flujos, una fuente de verdad.

Acceso a Datos.

entidades
  • Hogar — id, nombre
  • Usuario — id, nombre, email, hogar_id
  • Producto — id (ref. Odoo), nombre, categoría, código de barras
  • LarderItem — id, hogar_id, producto_id, estado, actualizado_en/por
  • ListaItem — id, hogar_id, producto_id, estado, creado_en, comprado_en/por
  • LarderEvento — id, larder_item_id, estado_anterior, estado_nuevo, fecha
relaciones y claves
  • Hogar 1—N Usuario, LarderItem, ListaItem
  • Producto 1—N LarderItem, ListaItem
  • Usuario 1—N LarderItem / ListaItem
  • LarderItem 1—N LarderEvento
  • Producto usa el id de Odoo, no se duplica la clave
casooperaciones
1 — Marcar productoLeer LarderItem · Modificar LarderItem · Crear LarderEvento · Crear ListaItem (si se_acabo).
2 — Consultar la listaLeer ListaItem · Modificar ListaItem (comprado) · Modificar LarderItem (vuelve a "bien").
desde → haciaqué dato viajacuándo
React → BackendCambio de estado de un producto en LarderAl tocar un producto
Backend → PostgreSQLNuevo estado + evento de LarderAl confirmar el cambio
Backend → OdooConsulta de nombre/categoríaProducto nuevo
Odoo → BackendFicha del productoRespuesta a la consulta
React → BackendMarcar ítem de lista como compradoAl tocar "comprado"
Backend → PostgreSQLActualización de ListaItem + LarderItemAl confirmar la compra

Decisión clave: Larder y List viven en PostgreSQL, propio del backend. Odoo solo se consulta para el catálogo — nunca escribe en la base de datos de Larder ni al revés.

La pantalla que va a React Native
CuálLarder — marcar productos.
